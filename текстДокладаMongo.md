## Вступление к блоку Mongo

Мы уже разобрали, как PostgreSQL кладёт данные на диск: страницы, версии строк, журнал предзаписи, индексы.
Теперь посмотрим на другую школу — документоориентированное хранилище на примере MongoDB.

Это другой контракт с данными: единица хранения — документ, а не строка таблицы с жёсткой схемой столбцов.
Если перенести мышление «как в третьей нормальной форме» один в один, получите дорогие связи между документами и разочарование в производительности.
Если спроектировать документ под то, как вы реально читаете и пишете, Mongo часто оказывается очень удобной для сервисов на Java.

Сегодняшняя дорожка такая:

1. Основы: модель, BSON, типы, команды, идея хранения.
2. Практика: `demo-mongo` + shell CRUD на его же `demo.orders` (`postgrvsmongo` - отдельно).
3. Внутренности: движок WiredTiger — зачем его сделали основным, чего добились, как устроен.
4. Закрепление по Spring (тот же `demo-mongo`, без второго стенда).
5. Если останется время — сравнение с PostgreSQL на графиках из бенчмарка (слайды, без живого `postgrvsmongo`).

## 1. Основы MongoDB

### Где место среди видов хранилищ

Напомню короткий тезис из классификации.
Документоориентированная база хранит иерархический объект целиком.
Сильное место — эволюция полей без миграции «добавь колонку во все таблицы» и чтение целого агрегата одним запросом.
Слабое место для тех, кто мыслит только JOIN'ами: связь «много коллекций как много таблиц» без аккуратной модели быстро становится болью.

В реляционной базе у вас таблица заказов, таблица строк заказа, внешние ключи, каскады.
В Mongo типичный заказ часто лежит одним документом: шапка и массив позиций внутри.
Это не «отсутствие нормализации навсегда», а выбор: что читается вместе — лежит вместе.

### Иерархия: база → коллекция → документ

У каждого документа есть идентификатор `_id`.
Если не задали сами — сервер сгенерирует ObjectId.
Это не то же самое, что serial в PostgreSQL, но роль похожа: стабильный первичный ключ документа.

### BSON

JSON удобен людям и API. Для СУБД его мало: мало типов, нет длин полей, медленнее обход.
Mongo снаружи «JSON-first», внутри использует **BSON** (Binary JSON) — бинарную сериализацию тех же вложенных документов и массивов.
Спека: https://bsonspec.org/

Чем BSON отличается от JSON:

- бинарный, не текст; глазами не читается без оболочки/IDE;
- в записи есть размер документа и тип каждого поля — движку проще обходить документ;
- типы шире: Date, BinData, ObjectId, отдельно int32 / int64 / double / Decimal128;
- в JSON число одно («number»), целые и дробные не разделены.

Зачем так сделали:

- мало накладных расходов (lightweight);
- быстрый обход (traversable) — BSON основной формат хранения Mongo;
- быстрый encode/decode (efficient);
- больше типов; поиск/скан полей быстрее за счёт метаданных длины и типа.

Гибкость как у JSON: без жёсткой схемы. Цена — имена полей лежат **в каждом** документе (в PostgreSQL имя столбца в каталоге один раз). Плотность чуть хуже, чем у форматов со схемой вроде protobuf.

Пример про целые без перевода в строку.
Большой идентификатор в JSON часто пишут строкой — иначе в JS теряется точность (`Number.MAX_SAFE_INTEGER`), в Java потом `Long.parseLong` / `toString`.
В BSON это **int64**: драйвер пишет и читает `long` / `Long` напрямую.

Лимит документа в Mongo — 16 МБ. Тяжёлые файлы в документ не кладут.

Типы на практике (Java): ObjectId, string, bool, int/long, double / Decimal128, Date, массив, вложенный документ, BinData, null.

Слайд: заказ с `_id`, `tenant_id`, `status`, `lines: [{ sku, qty }]`.

### Концепт хранения одной фразой

В PostgreSQL мы говорили: с диска приходит страница, внутри — версии строк.
В Mongo атом, о котором думает прикладной разработчик, — **целый документ**.
Прочитали заказ — получили шапку и позиции вместе, если вы так спроектировали.
Обновили одно поле — для движка это правка записи документа (часто с переписью значения), а не «ячейка столбца в куче».

Отсюда два практических следствия, которые потом повторим на WiredTiger:

1. То, что читаете вместе — кандидат лежать вместе (вложение).
2. Неограниченно растущий массив внутри документа — ловушка: документ толстеет, упирается в лимит, дороже пишется.

### Связи: вложение и ссылка

Вложение (embedded): позиции заказа внутри заказа.
Плюс — один запрос, локальность данных.
Минус — документ растёт; общий справочник так дублировать больно.

Ссылка: в документе лежит идентификатор из другой коллекции.
Плюс — справочник один.
Минус — нет настоящего внешнего ключа как в PostgreSQL.
Нет каскадного удаления «из коробки».
Нет автоматического обновления всех ссылок, если вы переименовали или пересоздали сущность.
При чтении «соединение» делается либо в приложении, либо стадией `$lookup` в конвейере агрегации — это по сути левое соединение при чтении, а не ограничение при записи.

Для аудитории одной фразой:
`$lookup` похож на JOIN по смыслу результата.
По гарантиям — нет: это не FK.

### Базовые команды (обзор до практики)

Язык запросов — не SQL, а методы оболочки / драйвера над коллекцией.

Создание и запись:

- `insertOne` / `insertMany`

Чтение:

- `find` / `findOne`
- фильтр — документ-условие: `{ status: "PAID" }`, диапазоны, `$in` и т.д.
- проекция — какие поля вернуть (это про форму ответа, не про «столбцовое хранение»)

Изменение:

- `updateOne` / `updateMany` с операторами `$set`, `$push`, `$pull`, `$inc` …

Удаление:

- `deleteOne` / `deleteMany`

Индексы:

- `createIndex`
- `getIndexes`

План и факты выполнения (ближайший родственник `EXPLAIN ANALYZE`):

- `explain("executionStats")`

Служебное:

- `use <база>`
- `show collections`
- `db.orders.stats()`

Синтаксис и CRUD покажем через `demo-mongo` (REST) и при необходимости в оболочке на тех же данных — сейчас важна карта.

## 3. Внутреннее хранение и WiredTiger

### Зачем вообще говорить про движок

С приложением вы говорите документами и коллекциями.
На диске работает хранилищный движок.
До версии 3.2 у Mongo по умолчанию был MMAPv1.
С 3.2 по умолчанию — WiredTiger.
Позже MMAPv1 убрали из актуальных веток: дорога одна, и это WiredTiger.

Переход был не косметический.
Для продакшена это сменило модель блокировок, сжатие, поведение под смешанной нагрузкой.
Имеет смысл понимать, *чего* добились и *ценой чего* — иначе «Mongo медленная/быстрая» остаётся мифом.

### Что бесило в старой модели (коротко)

MMAPv1 опирался на отображение файлов в память и грубые блокировки: по сути конкуренция писателей на уровне коллекции сильно ограничивала параллельную запись в разные документы одной коллекции.
Сжатия как у современного движка не было.
Для простых сценариев с редкой записью это ещё жило; для общего назначения сервисной нагрузки — потолок был виден.

### Какой фурор и чего добились с WiredTiger

Слайд: «было → стало».

1. **Параллелизм на уровне документа.**  
   Разные клиенты могут одновременно менять разные документы одной коллекции.
   Для Java-сервиса с пулом потоков и множеством мелких апдейтов это ночь и день по сравнению с «коллекция на замок».

2. **Сжатие данных и индексов.**  
   На диске коллекции по умолчанию жмутся (часто snappy), индексы — префиксным сжатием.
   Меньше места, лучше плотность в файловом кэше ОС.
   В обмен — CPU на сжатие/разжатие.

3. **Предсказуемая модель долговечности: журнал + контрольные точки.**  
   Похожий по духу сюжет, что мы разбирали у PostgreSQL с WAL: сначала зафиксировать изменения так, чтобы пережить крах, потом аккуратно закрепить снимок данных в файлах.

4. **Многоверсионность внутри движка.**  
   Читатель видит согласованный снимок на момент операции; писатели меньше мешают друг другу грубыми блокировками.

Итог для инженера: Mongo перестала быть «движком для узкого класса нагрузок» и стала гораздо более универсальным документохранилищем.
Не серебряная пуля, но другая весовая категория.

### Как этого добились: архитектура простыми словами

Слайд со схемой WiredTiger / BSON (по желанию - отдельный слайд в презентации).

Слои:

1. **Слой Mongo** — базы, коллекции, BSON-документы, каталог `_mdb_catalog` (какие коллекции на какие файлы отображаются).

2. **Слой WiredTiger**  
   - кэш страниц (в кэше данные коллекции разжаты — это важно для оценки RAM);  
   - B-деревья коллекций и индексов (это не LSM и не «уровни SST», как у некоторых key-value движков);  
   - на странице в памяти свежие вставки живут в упорядоченных списках с пропусками (skip list) до пересборки страницы на диск — деталь реализации, для доклада достаточно фразы «правки сначала в памяти страницы, потом сверка на диск»;  
   - журнал между контрольными точками;  
   - контрольные точки периодически закрепляют снимок в файлах.

3. **Файлы в каталоге данных**  
   - `collection-…` — RecordId → BSON;  
   - `index-…` — ключ индекса → RecordId;  
   - метаданные WiredTiger;  
   - файлы журнала.

Параллель с PostgreSQL, которую аудитория уже слышала:

| PostgreSQL | Mongo / WiredTiger |
|------------|-------------------|
| страница heap, tuple, ctid | блок/страница B-дерева, запись, RecordId |
| индекс → ctid → heap | индекс → RecordId → документ |
| WAL | journal |
| checkpoint / сброс грязных страниц | checkpoint в файлы `.wt` |
| строка = набор столбцов в tuple | документ = BSON целиком |

Почему индекс ускоряет — та же педагогика:
без индекса движок перебирает документы коллекции;
с индексом сужает набор RecordId, потом читает нужные документы.
Платим местом и работой на каждую запись/обновление: нужно обновить и дерево данных, и деревья индексов (часто в одной записи журнала вместе с клиентской операцией).

Документное хранение = «строковое» в том смысле, что поля одного объекта лежат рядом.
Настоящее столбцовое хранение (одно поле по миллионам объектов для аналитики) — другая модель; обычные коллекции Mongo под это не заточены.
Здесь сравнение с тем, что вы уже говорили про строковое и столбцовое в реляционном мире — уместно одной фразой, без углубления в проекции.

### Плюсы и минусы WiredTiger / модели документа

Плюсы:

- хорошо читается и пишется целый объект;
- параллельные апдейты разных документов;
- сжатие на диске;
- гибкая эволюция полей;
- понятный атом для сервиса и для кэша.

Минусы и цена:

- рабочий набор должен помещаться в кэш движка, иначе начинается просадка;
- раздутый документ и частые правки большого BSON дорого пишутся;
- много индексов бьют по записи;
- соединение коллекций при чтении дороже, чем аккуратный локальный документ;
- нет реляционных внешних ключей и каскадов;
- лимит 16 МиБ на документ.

Практический вывод (мостик к советам):
проектируйте под путь доступа; ограничивайте размер агрегата; справочники выносите ссылкой; индексы — только под реальные запросы; не ждите от Mongo поведения PostgreSQL с FK.

## 4. Mongo из Spring (тот же `demo-mongo`)

Отдельное приложение не поднимаем: практика уже шла на `demo-mongo`.
Этот блок - закрепление для Java-аудитории: таблица аннотаций и concern, если не успели вживую.

Это Spring Data MongoDB, не JPA.
Путать аннотации вредно: `@Entity` здесь ни при чём.

### Соответствие привычным вещам JPA

Слайд-таблица:

- `@Entity` → `@Document`
- `@Table` → `@Document(collection = "…")`
- `@Id` → `@Id` (часто String / ObjectId, без `@GeneratedValue` как в JPA)
- `@Column` → `@Field("tenant_id")` если имя в BSON другое
- `JpaRepository` → `MongoRepository`
- derived-методы (`findByTenantId`) работают так же по имени
- `@Query` — не JPQL, а JSON-запрос Mongo
- индексы — `@Indexed`, `@CompoundIndex`, при желании автосоздание на старте

В демо класс `Order`: коллекция `orders`, составной индекс по арендатору и дате, уникальный sparse по email, вложенный список `LineItem` - вложение на hot path.

### Concern (только теория, без живого lag)

В коде есть профили `strict` / `loose` (`MongoConcernConfig`): write/read concern и read preference.
На показе достаточно профиля `strict` (majority + primary) и отсылки к CAP из вступления.

Живой сценарий «POST на primary → сразу GET с secondary → 404 из-за lag» **не делаем**: на локальном RS с крошечной нагрузкой отставание почти никогда не ловится, пример выглядит сломанным.

Идея для аудитории:
одно приложение - одна модель; REST пишет, IDE и оболочка показывают тот же документ.

## 5. Сравнение PostgreSQL и Mongo (если есть время)

Полный прогон бенчмарка в живую может съесть полчаса.
Честный формат «если осталось 5–10 минут»: слайды с графиками из проекта `postgrvsmongo`, без обещания повторить все цифры на ноутбуке в зале.

Что сравнивали по задумке стенда:

- PostgreSQL нормализованный (таблицы + соединения);
- PostgreSQL с JSONB;
- Mongo с тегами внутри документа;
- Mongo, где теги через `$lookup` (ближе к соединению со справочником).

Операции вроде поиска по тегу, обновления, агрегатов — смотрим задержки (p50/p95) и характер деградации.

Что проговорить по графикам, даже без идеальных цифр:

1. Когда читаете «весь объект» и он спроектирован под запрос — документная модель часто выглядит сильно.
2. Когда начинаете соединять коллекции на горячем пути — вы платите за нормализацию примерно тем же классом проблем, что и за JOIN, плюс без FK.
3. JSONB в PostgreSQL — мост между мирами: реляционный движок, документ внутри; не нужно мифологизировать «только Mongo умеет JSON».
4. Выбор — про путь доступа, инварианты и навыки команды, а не про религию SQL/noSQL.

Если времени нет — один слайд «куда смотреть в репозитории» и ссылка на `postgrvsmongo`.
