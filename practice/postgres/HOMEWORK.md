# HOMEWORK: PostgreSQL

Четыре практики: индексы, партиции, шардирование (Citus), репликация. Выполняйте **по очереди**. Ничего сдавать не нужно.

Клиент: `psql`, IntelliJ Database или DBeaver. Готовые SQL и команды Docker - в [ANSWERS.md](ANSWERS.md).

## 1. Индексы

- [ ] Поднимите PostgreSQL для этой практики (локально или в контейнере)
- [ ] Подключитесь к базе
- [ ] Создайте таблицу `orders`: `id`, `tenant_id`, `status`, `created_at`, `email`, `amount`

Воспроизведите поведение (смотрите план через `EXPLAIN ANALYZE`):

- [ ] Поиск по селективному полю (`email`): без индекса - Seq Scan, после индекса - Index Scan
- [ ] Индекс по `status` при перекосе данных: частый статус часто идёт Seq Scan, редкий - Index Scan
- [ ] Частичный индекс (`WHERE status = 'PAID'`): подходит только запросу с этим статусом
- [ ] Составной индекс `(tenant_id, created_at)`: помогает при фильтре по обоим полям, не помогает при фильтре только по `created_at`
- [ ] `lower(email) = ...` не использует обычный индекс по `email`; expression-индекс `((lower(email)))` - использует

- [ ] Остановите эту базу перед следующим заданием

## 2. Партиции - ключ и типичный фильтр

**Цель:** понять, что партиционирование помогает только когда ключ совпадает с условиями запросов.

- [ ] Поднимите PostgreSQL для этой практики (локально или в контейнере)
- [ ] Создайте базу (например `part_hw`) и подключитесь к ней

**Данные**

- [ ] Создайте таблицу `events` с полями: `id`, `region_id`, `created_at`, `payload`
- [ ] Партиционируйте `events` **по списку** `region_id` (минимум 3 партиции: регионы 1, 2, 3)
- [ ] Заполните примерно **1 000 000** событий за несколько месяцев; сделайте перекос: большинство строк в регионе 1
- [ ] Обновите статистику (`ANALYZE`)

**Кейсы**

- [ ] Выполните запрос «сколько событий за один месяц» - фильтр **только по `created_at`**, без `region_id`
- [ ] Посмотрите план (`EXPLAIN ANALYZE`) - должны читаться все партиции (partition pruning не срабатывает)
- [ ] **Вопрос:** почему запрос медленный? Что сделать с ключом партиционирования?
- [ ] Остановите эту базу перед следующим заданием

## 3. Шарды через Citus

- [ ] Поднимите кластер Citus (coordinator + workers) локально или в контейнерах
- [ ] Подключитесь к базе на coordinator, включите расширение `citus`, зарегистрируйте worker-ноды
- [ ] Создайте таблицы для JOIN:
  - `orders` - distributed по `tenant_id` (плюс поле для связи со справочником, например `device_type_id`)
  - `payments_colocated` - distributed по `tenant_id`, `colocate_with` = `orders`
  - `payments_other` - distributed по другому ключу (например `payment_provider_id`)
  - `device_types` - reference table

Воспроизведите соединения:

- [ ] JOIN `orders` + `payments_colocated` по `tenant_id` (и `order_id`) - выполняется
- [ ] JOIN `orders` + `device_types` (reference) - выполняется
- [ ] JOIN `orders` + `payments_other` по `order_id` при разных ключах шардирования - **не выполняется**: перед запросом `SET citus.enable_repartition_joins TO off` (иначе Citus может сделать дорогой repartition)

- [ ] Остановите кластер Citus

## 4. Репликация

Инструкции и команды — в [`REPLICA.md`](../../REPLICA.md) в корне репозитория (из корня репо). Порт **5580** общий: async, sync и logical **не параллельно**; после каждого сценария — `down -v`.

**Async и sync**

- [ ] Поднимите и настройте **async** по REPLICA (до шага с pgbench **20** секунд)
- [ ] Запишите число транзакций за 20 секунд (строка **`number of transactions`** в выводе pgbench)
- [ ] Остановите async-стенд (`down -v`)
- [ ] Поднимите и настройте **sync** по REPLICA (до pgbench **20** секунд)
- [ ] Запишите число транзакций за 20 секунд
- [ ] Сравните async и sync: где больше транзакций и почему (primary ждёт standby при sync)

**Logical**

- [ ] Остановите async/sync, если ещё подняты
- [ ] Пройдите сценарий **Logical** в REPLICA от поднятия стенда до проверки репликации (шаги 1–5)
- [ ] Убедитесь, что INSERT на primary виден на subscriber
- [ ] Остановите logical-стенд
